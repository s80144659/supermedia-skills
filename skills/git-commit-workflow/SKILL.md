# Git 提交工作流程

使用本技能將未整理的工作樹整理成有意圖的提交，同時避免遺失使用者既有工作。

完整提交檢查清單見 `references/commit-checklist.md`；需要拆分 commit、同檔混有多件事、或需要確認文件/技能/任務脈絡是否同步時讀取。

## 作業流程

1. 暫存前先檢查 `git status --short` 與相關差異。
2. 依單一責任分組：功能、錯誤修正、重構、測試、文件、工具或產生物。
3. 不把無關檔案或無關變更區塊放進同一個提交。
4. 若同一檔案包含多個變更，只暫存屬於目前提交的變更區塊。
5. 提交前用 `git diff --staged` 重新檢查已暫存內容。
6. 檢查相關文件、技能或任務來源是否因規格或實作變更而漂移。
7. 透過 Notion MCP 查詢任務列表或專案列表最新 30 筆，取得對應的 TSK 編號附於標題尾端；找不到對應任務時繼續提交，不阻擋流程。
8. 執行能證明已暫存行為的最小驗證；若無法驗證，說明原因。
9. 提交訊息使用統一格式：`[type] 摘要 (TSK-編號)`；無對應任務時省略 `(TSK-編號)`。

## 安全規則

- 除非使用者明確要求，絕不執行 `reset`、`restore` 或丟棄你沒有建立的工作。
- 不暫存本機環境檔、機密、編輯器狀態、快取或產生雜訊。
- 提交包含資料庫遷移或資料結構變更時，提交前確認遷移順序與回復限制。
- 若文件、技能、產生的 API 結構或鎖定檔預期會變更，檢查是否需要和程式碼一起暫存。
- 不同審查或回復風險的變更，優先拆成多個一致的提交，而不是混在一起。
- `type` 使用簡短英文分類，例如 `feat`、`fix`、`docs`、`chore`、`refactor`、`test`。
- 摘要使用中文為主，描述這個提交實際改變了什麼。
- 不在提交主旨尾端附加 skill 名稱、流程分類或其他括號註記，除非使用者明確指定。
- 複雜提交在主旨後補充 body，固定使用 `Why:`、`What:`、`Impact:` 三段標籤，三段都要寫；簡單提交維持單行，不加 body。

## 回覆檢查清單

- 說明提交包含的主題與刻意排除的變更。
- 回報實際 commit message。
- 回報已執行或無法執行的驗證。
- 若工作樹仍有未提交內容，說明它們是否與本次提交無關。

## 停止條件

遇到以下情況，繼續前應停止並詢問：

- 使用者要求改寫歷史，但目標分支或協作狀態不清楚。
- 工作樹含有無法安全分離的無關變更。
- 需要執行破壞性 Git 操作。
- 資料庫遷移、產生物或第三方 vendor 檔案的歸屬不清楚。
- 相關文件、技能、任務或 issue 歸屬不清。
- commit message type 無法判斷。
- migration 時序與部署或回復路徑可能衝突。
