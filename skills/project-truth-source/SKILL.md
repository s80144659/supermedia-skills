# 專案真相來源

當規格、程式碼、測試與文件可能不一致時，使用本技能讓專案工作維持在可追溯的真相來源上。

## 核心規則

- 將明確指定的規格與決策文件視為預期行為來源。
- 將程式碼與測試視為目前可執行行為來源。
- 預期行為與可執行行為衝突時，先列出衝突；若本次任務已明確要求改變舊行為，可在回報影響後繼續。
- 最新明確決策優先於較舊的產生文件，但要記錄此優先順序，不要默默假設。
- 完成前重新檢查變更過的檔案、測試與產生文件，確保回覆符合工作區實際狀態。

## 真相優先順序

當來源不一致時，依序判斷：

1. 使用者在本次任務中明確給出的決策或限制。
2. 最新且已核准的規格、任務、決策紀錄、API 契約或發布決策。
3. 目前程式碼、測試與資料庫結構所呈現的可執行行為。
4. 由程式碼產生的文件、範例、截圖或快照。

若較高順位來源與可執行行為衝突，先列出差異與影響層；只有在需求未決或牽涉資料破壞、認證、授權、安全、合規時，才停止請使用者決策。

## 規格文件修訂原則

- 主規格文件以目前有效規則為主，不把草稿、歷次修訂或討論過程堆進正文。
- 會被追究、容易誤解、或會影響實作與稽核的決策變更，才在對應段落旁加短的「決策註記」。
- 決策註記應說清楚現行規則、取代的舊假設、決策原因或追溯入口；不要把完整討論過程塞進註記。
- 最近高影響變更可放「修訂紀錄」摘要；完整背景、替代方案、責任脈絡放「決策紀錄」或「決策說明」。
- 文案以繁體中文與台灣團隊常用術語為主。除軟體工程專有名詞、工具名、程式碼識別字、API 欄位或產業通用縮寫外，避免使用不必要英文。

## 標準輸出

實作或審查工作應包含：

1. 影響層：資料庫、服務、控制器、中介層、路由、資源、工作、排程、文件、測試。
2. 已同步產物：相關控制器、服務、政策、資源、遷移、元件、客戶端、結構、測試、文件。
3. 邊界檢查：認證、授權、租戶/專案隔離、狀態機、速率限制、稽核日誌、資料契約、UI 狀態、客戶端契約。
4. 驗證：實際執行的指令與是否通過。

## 停止條件

遇到以下情況，停止並請使用者決策：

- 需要破壞性資料變更。
- 規格對認證、金額、資格、狀態轉換、通知或法務/合規行為互相衝突。
- 唯一可用來源已過期，或明確標示為草稿。
- 某個測試保護的行為看起來已被最新產品規則退場。
