# 既有產品介面的迭代設計

先判斷使用者正在完成什麼工作，再決定輔助資訊如何出現。交付可編輯的改稿，並在對話簡述修改區塊、結果與定位連結；額外的展示或說明依使用者要求保留。

## 作業流程

- 先讀取目前設計與使用者指定的原生參考節點，保留上次操作後的人工修改。對話中的產生圖片只能輔助討論，不能取代指定稿的元件、字型、色彩、間距與互動語彙。
- 從 user story 確認主要工作、輔助資訊的查閱頻率、需要同時對照的內容，以及必要與選填輸入。缺少的資料會改變設計選擇時才追問，不先預設某個視窗或展開模式。
- 區分產品規則與設計假設。角色可做的操作、資料可見範圍、判定與統計條件依所屬產品來源，不由樣稿或常見 SaaS 寫法補出。

## 決定呈現與狀態

| 可觀察情境 | 設計判斷 |
| --- | --- |
| 輔助資料偶爾才查閱 | 在原工作附近提供可辨識入口，需要時再揭露，返回後保留填寫內容與操作位置。 |
| 經常需要並列比對 | 評估原地展開或並排；同時考慮長內容會占用多少主要工作空間。 |
| 通常只關心多項資訊中的其中一項 | 讓使用者定位並查看該項，不擅自指定哪一題最重要；依項目數量選擇清單、單項展開或查找方式。 |
| 只有平台、帳號或樣本文字不同 | 使用一份代表稿與資料差異註記。互動、可見內容或驗證規則不同，才增加獨立狀態。 |
| 輸入可由既有上下文或可靠的後續處理取得 | 評估移除重複選擇；若使用者選擇會改變結果或辨識不足，保留必要輸入。 |

為了示範可點擊操作，不必複製每個資料值或所有值的組合。原型工具受限時，保留足以解釋行為的必要狀態，註明未模擬的操作；不要把原型限制轉嫁為大量重複整頁。

限制文案若涉及先前選定的對象，可在對應詞語提供回查入口。顯示此次操作的相關資料，避免導向一般設定頁後讓使用者重新尋找。選填的補充資料與主要工作成果應能辨識，標示會影響使用者決定的用途或範圍，不把後端處理細節塞進操作流程。新增補充入口時，核對舊限制註記的適用範圍，避免把主要成果的規則誤套到補充資料。

## 元件與交付範圍

- 元件屬性只對應已確認的配置需求。版型固定時使用單一元件，不預先為每段內容增加屬性或開關。
- 套用元件時不自行覆寫實例的文字、素材、可見性、筆數或樣式，也不為保留舊樣稿而隱藏主元件內容。資料差異只有使用者明確要求時才處理，交付時揭露實際覆寫範圍。替換前先盤點既有覆寫；歸屬不明的人工修改先釐清，不以整批重設取代判斷。
- 不自行填寫元件的 `description` 或說明欄位；用途與修改摘要放在對話。使用者要求清除描述時，只清除指定範圍。
- 預設保留主元件與實際頁面的實例，並優先用它們驗證。使用者明確要求預覽、展示、介紹或比較稿時才另外保留；暫存驗證稿完成後依確切節點 ID 清理，不依模糊名稱批次刪除。

## 修改與驗證

- 沿用既有元件與樣式，新增內容保持可編輯圖層。若使用者要自行評估元件化，先保留區塊結構，不擅自新增主元件。
- 寫入前確認節點仍符合剛讀到的結構。小幅改動以局部修改為主，避免重建無關頁面或覆蓋人工編排。
- 若畫面含紫色文字等浮動規格註記或箭頭，替換前必須截圖，範圍包含註記與所指內容，並讀取原文、提示條件、資料限制與操作意義。註記不納入產品元件，也不因元件化刪除。
- 替換後以相同範圍再次截圖，核對註記原意及指向。版面高度改變時，依所指區塊同步校正註記、箭頭及關聯示意視窗；只保留文字或座標不算保留語意。指向不明或會改變原意時先說明。
- 套用後逐層比對主元件與實例的文字、可見性、素材筆數、字型、色彩、間距與尺寸，並檢查實例覆寫。不同容器寬度使用同寬參照比對，將容器伸展與內部覆寫分開回報；不能只以主元件 ID 相同宣稱外觀一致。
- 區分編輯畫布的定位連結與 Prototype 的產品互動。使用者要在畫布點選跳轉時，另外設定指向正確節點的文字連結；需要示範 popup 時保留 overlay 互動，分別驗證目的地。
- 驗證長文字、空值、收合與展開、輔助入口返回，以及修改涉及的連結。依改動範圍檢查原生渲染，不將整頁截圖或點擊連結存在當成所有狀態都正確。
- 工具宣告某項能力或方法存在，不代表該操作已完成。只有實際成功回應、版本 ID 或讀回結果才能支持「已儲存／已建立版本」等交付敘述。

## 標準輸出

每輪修改後，依功能或共用區塊精簡說明差異、必要的精確連結與已驗證事項。同一變更合併說明，不逐頁重列；審查者可直接找到實際修改處。 元件替換的檢查連結直接指向實例，不只指向外層容器。

使用者要求在設計檔內回查時，才依工具實際能力建立具名版本、修改索引或局部前後對照。先後版本與對照資料須有真實來源，無法建立版本時明確說明；未要求索引時，保留對話中的修改摘要與定位連結即可。

Notion 需求以少量條列說明情境、預期行為及關鍵限制，畫面細節交給設計稿。引用 Figma 使用帶畫面名稱的一般文字連結，保留完整節點網址，不轉成嵌入、書籤、預覽或外部整合物件；回讀確認 MCP 可取得目標網址。

需求、進度與設計紀錄寫入使用者指定的位置與欄位。目的地只授權更新狀態時，不附帶改寫需求描述、註解或其他文件。

## 停止條件

- 指定節點與目前畫面不同，或來源衝突會影響角色、資料或操作範圍：先定位差異，再決定是否需要使用者確認。
- 需要覆蓋無法辨識歸屬的人工修改，或工具失敗後無法判斷已寫入範圍：先讀回現況。
- 產品規則未決，卻必須靠新增欄位、角色能力或預設選項才能繼續：將未決處帶回討論。
