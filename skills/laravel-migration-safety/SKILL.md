# Laravel 資料庫遷移安全

資料庫遷移是正式環境歷史。除非確定遷移尚未部署，否則以只新增不回改的方式處理。

## 快速流程

1. 判斷部署狀態：已部署、未部署或未知。
2. 若已部署或狀態未知，新增向前遷移，不編輯舊遷移。
3. 若尚未部署，只有在記錄誰需要重新執行遷移後，才可編輯原遷移。
4. 識別資料影響：資料表、欄位、索引、外鍵、列舉/狀態值、資料回填、不可逆變更。
5. 新增或更新受資料結構變更影響的測試、factory、seeder、API Resource 與文件。
6. 執行能證明變更的最小遷移/測試指令。

## 部署證據

依序查找專案可用證據：`migrate:status`、正式環境 migrations table、release notes/tag、deployment pipeline、DBA 或 owner 確認。找不到可靠證據時，標記為未知並採用已部署處理。

## 遷移決策表

- 已部署或部署狀態未知：新增向前遷移，並保留舊遷移歷史。
- 確認尚未部署：可編輯原遷移，但要記錄需要重新執行遷移的人或環境。
- 破壞性變更：優先拆成新增欄位、雙寫或相容讀取、回填、切換、清理的階段。
- 大量資料回填：優先使用可重試、分批、具保護條件的方式；不要把長時間或不可重試操作塞進無保護遷移。

## 安全規則

- 除非使用者明確要求，不改既有遷移的時間戳。
- 刪除欄位、資料表、索引或資料前，必須明確指出資料損失。
- 修改 Laravel 欄位時，在遷移中保留既有屬性。
- 分階段發布時，破壞性清理前優先使用可空或追加式變更。
- 資料回填應具備冪等性或保護條件，讓它們可安全重試。
- 對應用事件時間，優先使用範圍符合產品需求的欄位型別；若 `timestamp` 的 2038 範圍限制或隱含時區行為有風險，避免作為預設。

## 停止條件

遇到以下情況，寫入或修改遷移前應停止：

- 變更會刪除或改型既有資料，但沒有發布、回填、回復或資料保留計畫。
- 使用者要求改已部署遷移，且沒有明確說明要改寫歷史。
- 部署狀態未知，同時變更包含刪除欄位、重命名欄位、改型、外鍵重建或大量回填。
- 資料回填不具冪等性，且重跑會造成重複副作用或資料污染。
- 正式環境資料量、鎖表時間或 rollback 不可行性會影響可用性，但尚未取得發布決策。

## 回覆檢查清單

- 部署判斷與選擇的做法。
- 資料影響與回復限制。
- 資料回填或相容性計畫。
- 已執行的測試與指令。
- 尚待決策的產品、DBA 或發布問題。
