# 測試審查流程

測試應保護產品承諾、風險邊界與回歸點，而不是偶然的實作細節。

## 測試價值判準

一支測試至少應符合以下其中一項：

- 驗證目前需求或業務規則。
- 保護高風險邊界：認證、授權、狀態轉換、租戶隔離、金額、速率限制、稽核日誌、API 契約。
- 防止已知回歸問題。
- 作為受支援流程的可執行文件。
- 以低維護成本覆蓋有意義的失敗或邊界路徑。

## 審查流程

1. 識別變更類型：主要流程、備援流程、導入流程、權限防護、API 契約、排程、匯入/匯出或狀態機。
2. 新增測試前先搜尋附近既有測試。
3. 對每個相關測試，確認它保護哪條政策，以及該政策是否仍存在。
4. 若核心測試仍有價值，更新過時載荷、名稱與斷言。
5. 未確認某測試不是受支援行為的唯一保護前，不要刪除。
6. 對外可觀察行為優先使用整合或功能測試；孤立領域邏輯使用單元測試。
7. 若測試不再屬於主要路徑，刪除前先判斷它是否仍保護備援、導入、相容性或已知回歸。

## 目的註解

當測試保護不明顯規則時，加入簡短目的註解：

```text
目的：驗證受支援流程會拒絕超過截止時間的提交。
```

描述外部承諾，不要描述內部實作技巧。

## 驗證

先執行最小相關測試指令；共享行為變更時再擴大範圍。若跳過驗證，說明原因與殘留風險。
